# Ornith-1.5 解説まとめ

## 結論：何がすごいか一言で
Ornith-1.5は、モデル自身が「練習問題を作る→解き方のコツを作る→解いてみる」を繰り返して自分で強くなる仕組みを完成させたオープンソースのモデルファミリーです。特にコーディングとエージェント的な作業で、同規模のオープンソースを大きく上回り、397B版はClaude Opus 4.8と同等、9B版はスマホでも動くサイズながら大規模モデルに匹敵します。

## 誰が作ったか
記事から特定の個人名や所属組織の詳細は分かりません。ブログの表記は Ornith Team、サイトは ornith.ai です。Ornith-1.0をベースに開発されたと記載されています。

## 何が新しいか

### これまでの自己改善との違い
Ornith-1.0は自己スキャフォールディング self-scaffolding を導入。Ornith-1.5はそれを end-to-end の自己改善ループに拡張しました。

日常のたとえで言うと、従来は先生が用意した問題集を解くだけ。Ornith-1.5は自分で「今の自分にちょうど良い難しさの問題」を作り、解くための手順書＝足場 scaffold を作り、実際に解いてみて、結果を元に問題作り・手順書作り・解き方を全部一緒に改善します。

### 学習の仕組みを噛み砕くと
1サイクルは3段階です。
* **タスク生成**：環境やコードベース、過去の解き方履歴を見て、今のモデルが解けそうで解けない、少し上の問題を提案
* **スキャフォールド生成**：その問題専用の指示・道具・分解戦略・進行手順を作る        
* **ロールアウト生成**：作った手順で実際に解いてみる

報酬は3段階すべてに伝播します。つまり「良い解き方」だけでなく「良い問題」「良い手順書 」を作る能力も強化されます。

### 報酬の考え方
**タスク報酬 R_task**
```
R_task = V(q,s) × D(q,s,{τ_i}) × N(q)
```
* V = 有効性・検証可能性。問題と手順書がきちんと動いて正解不正解を判定できるか。たとえで言うと、採点基準が明確なテストか。
* D = フロンティア難易度。成功率 p が目標 p* = 0.2 に近いほど高い報酬。簡単すぎず難し すぎず、ちょうど伸びる問題を好む。
  * p = 成功回数 / 試行回数
  * D = exp( -(p-p*)^2 / 2σ^2 )
* N = 新規性。過去のタスクとの類似度が低いほど高い。同じ問題の焼き直しを避ける。      

Vが0なら報酬は0になるハードゲートなので、壊れた問題は学習に使われません。

**ハーネス報酬 R_harness**
```
R_harness = C(q,h) × F(h,{τ_i}) × H(h)
```
* C = タスクとの整合性
* F = 報酬の忠実性。解の良し悪しを正しく評価できているか
* H = ハック耐性。抜け道で点数を稼げないか

**ロールアウト報酬 R_rollout**
```
R_rollout(τ_i) = h(q,τ_i)
```
生成されたハーネスがそのまま採点します。検証可能なタスクは合格/不合格、複雑な環境では 正しさ・完了度・効率・制約遵守を組み合わせます。

質問生成・ハーネス生成・解法ロールアウトはすべて GRPO で最適化され、3段階が連動して改 善します。

### スケールと性能
* スケール：397B MoE、35B MoE、9B Dense。9Bは量子化版 Ornith-1.5-9B-Mobile で iPhone/Android へ展開可能と記載。
* ベースは Ornith-1.0 で、Qwen3.5 と Gemma 4 をベースに continued pretraining、mid-training、post-training を施したもの。

主要数値
* Ornith-1.5-397B：Terminal-Bench 2.1 86.1、DeepSWE 56.0。Claude Opus 4.8 は 85.0 と 59.0。オープンソース同規模の GLM-5.2 は 82.7 と 46.2、DeepSeek-V4-Flash-0731 は 82.7 と 54.4。
* Ornith-1.5-35B：トークンあたり活性パラメータ約3Bながら、Terminal-Bench 2.1 で Gemma 4-31B 43.4、Muse Glimmer-30B 51.7 に対し 68.5。SWE-Bench Verified で 79.0 対 52.0 と 76.0。
* Ornith-1.5-9B：Terminal-Bench 2.1 47.0、SWE-Bench Verified 70.6。Gemma 4-31B や Qwen 3.6-35B を上回る結果。

## 現場での活用イメージ
* **開発**：コード生成・リポジトリ理解・バグ修正の自動化。特に Terminal-Bench や SWE-Bench 系で高いため、実務に近いエージェントタスクのプロトタイピングに使える。
* **企画**：自社ドメインのタスクをモデル自身に作らせるカリキュラム生成の発想を参考に、評価データの自動拡張や難易度調整の仕組みを検討できる。
* **運用**：9Bクラスはオンプレ・モバイル展開が現実的。社内ツール連携や軽量エージェントとして導入検討が可能。397B/35Bは高精度なレビュー・テスト生成に。

## 課題・注意点
* 自己生成タスクの品質管理。Vのハードゲートがあるとはいえ、壊れた問題や評価が曖昧な問 題が混ざると学習が歪むリスク。
* 報酬ハッキング耐性。Hで対策されているが、ハーネス自体が作られるため抜け道が学習され る可能性は残る。
* 評価条件の違い。ベンチマークは温度やコンテキスト長、タイムアウト、ハーネスが各々異なる。記事のフットノート参照の上で比較が必要。
* 計算コスト。自己改善ループはタスク生成・スキャフォールド生成・複数ロールアウトを繰り返すため、学習・推論コストが大きい。
* 再現性。結果は5回平均と記載されているが、環境依存が大きいタスクでは運用時のばらつき に注意。
