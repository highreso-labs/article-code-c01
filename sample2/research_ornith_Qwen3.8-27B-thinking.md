# Ornith-1.5 解説：AIが自分で「問題を出して、解いて、強くなる」仕組み

## 一言で何か

**Ornith-1.5** は、AIモデルが「自分で練習問題を考え → 解き方の戦略を立て → 実際に解いて → 正解かどうかで評価 → 次はもっと難しい問題を考える」というサイクルを回して、**自分で自分を強くしていく**オープンソースのAIモデル群です。

### 何がどのようにすごいのか

| すごい点 | 具体例 |
|---------|--------|
| 最大モデル（397B）が商用トップクラスと同等 | Terminal-Bench 2.1 で **86.1**（Claude Opus 4.8 は 85.0） |
| 最小モデル（9B）がスマホで動くのに、30B超のモデルより強い | SWE-Bench Verified で **70.6**（Gemma 4-31B は 52.0） |
| オープンソースで手に入る | Hugging Face に公開 |

## 何が新しいか（たとえ付き）

### 従来のAI学習 vs Ornith-1.5 の学習

**従来のやり方（人間が全部用意）：**

```
人間が問題集を作る → 人間が解き方のヒントを書く → AIが解く → 人間が採点
```

> たとえ：塾の先生が毎回、問題・解説・採点を全部やる。生徒（AI）はただ解くだけ。

**Ornith-1.5 のやり方（AIが全部やる）：**

```
AIが問題を出す → AIが解き方の戦略を立てる → AIが解く → AIが採点 → 次はもっと難しい問題を
```

> たとえ：生徒が自分で問題集を作り、解き方のコツも自分で見つけ、解いて、自分で採点して、次はもっと難しい問題に挑戦する。先生（人間）は最初だけ大まかな方向性を示すだけ。

### 3つの段階をもう少し詳しく

| 段階 | 何をしているか | たとえ |
|------|--------------|--------|
| ① タスク生成 | 「今より少し難しい問題」を自分で考える | 生徒が「ここが苦手だな」と思って問題を考える |
| ② スキャフォールド生成 | その問題を解くための「手順書・道具の使い方・分解の仕方」を作る | 解き方のメモや、使う道具の準備 |
| ③ ソリューション（ロールアウト） | 実際に問題を解いて答えを出す | 本番で問題を解く |

この3つが**全部一緒に強くなる**のがポイントです。解くのが上手くなると、より良い問題も出せるようになり、より良い解き方の戦略も思いつくようになります。

### 報酬（採点）の仕組みを噛み砕いて

AIが「良い問題を出したか」を採点するときに、3つの条件を**全部満たす**必要があります（どれか一つでもダメなら0点）：

| 条件 | 意味 | たとえ |
|------|------|--------|
| **有効性（V）** | 問題が正しく作れていて、採点もできるか | 問題文が意味不明じゃなく、正解が明確に判定できるか |
| **フロンティア難易度（D）** | 今の実力に「ちょうど少し難しい」か | 全問正解できる易しすぎても、全問不正解の難しすぎてもダメ。正解率 **20%（p\* = 0.2）** 付近が理想 |
| **新規性（N）** | 以前と似た問題じゃないか | 毎回同じ問題のバリエーションを出さない |

> **たとえ：** 生徒が「正解率20%くらいの問題」を自分で出せると、ちょうど「伸びしろがある」問題なので最も効率的に成長できる。全問正解できる問題ばかりだと成長しないし、全問不正解だと何が悪いか分からない。

「解き方の戦略（スキャフォールド）」の採点も同様に3つ：

| 条件 | 意味 |
|------|------|
| タスクとの整合性（C） | 問題の意図に合った戦略か |
| 報酬の忠実性（F） | 正解に高い点、誤答に低い点を付けているか |
| ハッキング耐性（H） | 不正なショートカットで点を稼がれないか |

これらはすべて **GRPO**（一種の強化学習手法）で最適化されます。

> GRPO のたとえ：「同じ問題を何回も解いて、うまくいった解き方とダメだった解き方の差から学ぶ」方式。正解の正解率が高い解き方を強化し、低い解き方を弱める。

## 現場での活用方法

### 開発チーム

| 活用シーン | どのモデルが向いているか | 理由 |
|-----------|------------------------|------|
| コードの自動修正・バグ修正 | 397B（サーバー）or 35B | SWE-Bench Verified 86 / 79 と高い。実際のGitHubリポジトリのissueを解決する能力 |
| 多言語コードの理解・変換 | 397B or 35B | SWE-bench Multilingual 79.6 / 71.4 |
| 社内ツールでのコード補完（オンプレミス） | 35B（MoE、実効3B） | 35Bだが1トークンあたり3Bしか使わないので、比較的に軽量に動かせます |
| スマホ/タブレットでのオフライン補完 | 9B（Mobile版） | iPhone・Androidにデプロイ可能。SWE-Bench Verified 70.6 |

### 企画・プロダクトチーム

| 活用シーン | 考えられること |
|-----------|--------------|
| 競合分析・リサーチの自動化 | 397B の BrowseComp 86.6、WideSearch 80.8。Web検索＋要約のエージェントとして |
| 社内ナレッジのQ&A | 35B の SWE Atlas QnA 39.8。コードベースやドキュメントに対する質問応答 |
| 小規模PoC（プロトタイプ） | 9B をスマホに載せて、データが外部に出ない環境での検証 |

### 運用チーム

| 活用シーン | 考えられること |
|-----------|--------------|
| サーバー/インフラのトラブルシューティング | Terminal-Bench 2.1 はターミナル操作のベンチマーク。397B が 86.1、35B が 67.8 |
| 監視・アラートの自動対応 | Agentic（エージェント）系ベンチマークが全体的に高い。ツールを呼び出して操作する能力 |
| 社内AIのセルフホスティング | オープンソースなので、データが社外に出ない環境で運用可能 |

### 「自分で強くなる」仕組みの現場への示唆

Ornith-1.5 の学習方式そのものはエンドユーザーが直接使うものではなく、**モデル開発側**の技術です。ただし、この思想は現場にも応用できます：

> **ヒント：** 社内AIエージェントを使うとき、「人間が全部プロンプトを書く」のではなく、「AIに『このタスクでうまくいかなかったパターンを自分で分析して、次のプロンプト案を出して』と依頼する」運用を考えると、Ornith-1.5 の自己改善ループに近い効果が得られる可能性があります。

## 課題・注意点

| # | 注意点 | 説明 |
|---|--------|------|
| 1 | **ベンチマークスコア ≠ 実業務での性能** | 記事の数字は特定のテスト環境での結果です。自社のデータ・業務にそのまま当てはまるとは限りません。必ず自社環境でPoCしてください。 |
| 2 | **397B は巨大** | 397BパラメータのMoEモデルです。推論に大規模GPUクラスタが必要です。一般の社内サーバーでは動かない可能性が高いです。 |
| 3 | **35B は「実効3B」** | MoE（Mixture of Experts）方式で、1トークンあたり3Bパラメータしか活性化しません。効率は良いですが、35B全体分のメモリは必要です。 |
| 4 | **9B の Mobile 版は量子化済み** | 「Ornith-1.5-9B-Mobile」という量子化版がスマホ向けです。精度が多少落ちる可能性があります。 |
| 5 | **ライセンス詳細が記事にない** | 「オープンソース」とは書かれていますが、具体的なライセンス（MIT, Apache 2.0, 商用利用可否など）は記事に明記されていません。導入前に Hugging Face のページで確認してください。 |
| 6 | **自己改善ループは学習時の技術** | 「AIが自分で強くなる」のは**学習（トレーニング）段階**の話です。一度学習が終わったモデルをダウンロードして使うだけでは、このループは回りません。 |
| 7 | **比較対象のバージョンに注意** | 記事では Claude Opus 4.8、GLM-5.2、DeepSeek-V4-Flash-0731 等と比較していますが、これらは記事執筆時点（2026年8月）のバージョンです。 |
| 8 | **5回平均** | 全結果は5回の独立実行の平均です。1回だけの実行では変動がある可能性があります。 |

## まとめ（結論）

- **Ornith-1.5 は「AIが自分で練習問題を考え、解き、強くなる」仕組みで学習されたオープンソースモデル群**です。
- 最大モデルは商用トップクラスと同等、最小モデルはスマホで動いて30B超より強い、という**サイズと性能のバランス**が最大の強みです。
- 現場では、**35B を社内サーバーに載せてコード支援やエージェント用途で使う**、**9B を端末に載せてオフライン利用する**、が現実的な第一歩です。
- 導入前にライセンス確認と自社環境でのPoCは必須です。
